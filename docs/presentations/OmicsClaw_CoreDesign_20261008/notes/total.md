# 01_cover

OmicsClaw 要解决的是从分析请求到可审核结果之间的执行问题。当前项目有八十八个技能，覆盖七个领域，其中八十三个提供函数库接口。今天按一次分析会遇到的问题，解释核心组件为什么需要存在，以及它们如何连接请求、执行和证据。技能数量表示能力目录的覆盖范围，不代表所有后端都已完成真实数据验证。

---

# 02_evolution

先看支撑方式为什么发生变化。较多依靠预设工作流的应用，把任务路径、分支条件和异常处理写在代码里，模型在指定节点完成判断。这种方式适合流程稳定、输入边界清楚的任务。随着工具调用、代码生成和多步推理能力发展，模型可以读取工具结果，再提出下一步动作；对于分析路径事先不完全确定的任务，运行时决策变得更可行。

灵活性也带来了工程要求：动作要经过权限检查，长任务需要管理上下文和状态，失败要反馈给后续判断，过程还要能观察和评估。Harness 指围绕模型行动循环提供这些支撑的运行环境。图中左侧强调预设路径，右侧强调判断、执行与观察的反馈循环，表达的是设计重心的变化；Framework 也可以承载这样的循环，固定工作流仍可作为其中的可靠工具。模型决定下一步的能力增强，并不自动保证整个任务可靠完成。

放到 OmicsClaw，质控结果、缺失依赖或某个方法的失败，都可能改变下一步分析。因此项目采用动态决策循环，同时保留科学方法的明确输入输出和模块回放。接下来从这些具体需求展开组件设计。

---

# 03_problem

这种运行时支撑在组学分析中有具体需求。实际分析通常需要多步调整：先查看数据，再确定方法，运行后还要根据结果改变参数。Python、R 和外部命令又有不同的依赖与输入要求。同时，上游变化会影响下游，报告中的结论需要能追到具体输出。因此，OmicsClaw 一方面组织方法和环境，另一方面保存步骤、依赖和验证依据。核心目标是让方法找得到、过程接得上、结果查得清。

---

# 04_map

先把系统看成一条请求流。CLI、Desktop 和 Channel 接收请求，entry 组装运行实例并管理会话；engine 调用模型，provider 处理模型接口差异，schema 定义共同消息。工具层把决策变成动作，权限与沙箱限定执行。科学技能和共享 SDK 产生分析步骤与结果。上下文、记忆、计划、子任务、环境和观测围绕这条路径提供支持。这里画的是职责关系，具体导入方向由代码边界约束。

---

# 05_engine

分析开始时往往还不知道所有后续步骤，所以需要一个能根据观察继续行动的循环。engine 把当前消息交给模型，模型提出工具调用，工具结果再成为下一轮的输入；不再请求工具时，返回最终回答。完整返回和流式输出共享同一个内核，减少两套行为分叉。循环管理执行预算和终止，但把提示构造、会话保存与具体科学方法交给其他组件。执行失败会抛出，取消也继续向外传播。

---

# 06_schema

如果模型接口、主循环和工具各说各话，每次新增能力都要修改多处转换逻辑。schema 提供共同语言：消息、工具调用、工具结果、用量和流式片段。它只依赖标准库，各层都可以使用它，自己不反向依赖项目的其他层。供应商差异留在适配器中。这样，模型适配、执行和工具可以分别演进，也减少了循环导入的问题。

---

# 07_provider

模型服务的请求格式、流式事件和错误并不一致。provider 把这些差异收在适配层，通过共同接口提供完整生成、流式生成和按需配置绑定。当前包括 OpenAI-compatible 与 Anthropic 适配。模型、温度和输出上限属于 provider 实例，engine 不必了解厂商配置。统一协议使替换模型更容易，但不会抹平模型本身的推理和工具选择能力，实际任务仍需评估。

---

# 08_tools

模型只能提出动作，真正的执行还需要找到本地实现。ToolRegistry 把注册、对模型暴露定义和按名称执行集中管理。模型看到名称、描述和参数结构，执行策略则留在工具层，部署决定哪些工具可见。读取文件、写入文件、编辑文件和运行命令承担基本动作，科学方法由脚本或分析步骤完成。新增方法因此不要求在主循环里不断添加算法分支；风险、审批和并发声明仍有明确归属。

---

# 09_prompt

模型每次判断都需要知道项目要求、可用方法和当前环境。如果这些规则散落在调用代码里，就难以检查和维护。PromptAssembler 接受有序的 Section，由 entry 决定顺序，把分析契约、安全规则、工具与计划指导、技能目录、环境和长期记忆摘要组装为系统消息。空段落跳过，各段有 token 估计，再与历史和当前请求一起发送。每类信息有明确来源，组件变化时可以局部更新。

---

# 10_skills

把八十八份完整方法说明一直放进提示，会挤占数据和结果的空间。技能加载采用先目录、后正文的方式：系统提示先给名称和描述，模型判断需要哪种方法，再通过 use_skill 读取完整说明与所在目录。SKILL.md 集中维护适用条件、跳过条件、接口与依赖。加载说明之后才通过 bash 运行脚本或分析步骤，再读取实际输出。说明文档负责指导选择，执行仍由工具完成。

---

# 11_context

即使技能按需加载，长分析也会积累大量日志和历史。context 先扣除输出预留、工具定义和安全余量，再决定历史可用预算。压力上升时，先将长输出卸载为文件引用，随后进行局部或全面总结，最后才采用紧急截断。压缩需要保留工具调用和结果的配对，否则后续判断会失去依据。它的意义是让有限窗口服务当前决策，而不是无限保留所有原文。

---

# 12_memory_plan

上下文压缩之后，仍要保留已知事实和未完成工作，但两者用途不同。memory 在工作区 SQLite 中保存会话，长期事实通过 FTS5 检索，并以有界摘要进入后续提示；压缩前先提取事实，后续轮次重新读取摘要。planning 用独立的 PlanBook 保存任务状态，每次模型调用前重新注入，并通过 plan_write 更新。恢复会话时还能还原进度。不过，计划写成完成只代表任务状态，不等于科学验证和用户验收已经通过。

---

# 13_entry

当分析从终端扩展到桌面和消息平台时，不宜为每个界面维护一套运行逻辑。entry 通过 build_app 统一组装模型、工具、提示、记忆、权限、沙箱和子任务。同一会话内的交换串行，避免历史相互覆盖；不同会话可以并发。每次交换有独立任务和可管理句柄，队列与事件缓冲有界，并支持观察和续接。只有成功的交换替换会话历史，从而把界面交互与运行管理分开。

---

# 14_recovery

分析失败不能统一理解为再试一次。参数或输入错误作为工具观察返回模型，由模型重新读取数据、修正参数，再决定是否调用。网络错误、限流和服务端暂时故障进入有预算的退避重试，其他客户端错误不盲目重试。当总时间预算耗尽或用户取消时，应当结束执行。取消不会回滚已经发生的文件操作，所以任务状态与文件状态仍需分别检查。这种分工让错误处理既能修正问题，也能及时停止。

---

# 15_permission

模型能够调用工具，并不意味着所有动作都应直接发生。PermissionGate 综合运行模式、规则和危险命令模式，给出允许、询问或拒绝，入口再负责向用户展示审批并接收决定。一次允许、会话允许和记住规则对应不同授权范围。只读模式也拒绝可以执行不受限子任务的委派。自动批准模式仍可能遇到危险动作与保护路径审批；命令模式匹配也无法穷尽所有绕过方式，因此还需要执行环境的限制。

---

# 16_sandbox

权限回答能不能做，沙箱进一步限定命令能接触什么。启用时，Docker 或 Podman 接管 bash，默认没有网络，项目代码只读挂载；分析工作区可读写，内部状态通过遮蔽和交换路径处理。宿主机文件工具另由 Workspace 限定路径。分析在本地运行，不代表所有信息都不出机器，因为 provider 仍可能发送上下文和工具结果给远程模型。执行隔离同样不提供对已完成副作用的自动回滚。

---

# 17_skillenv

方法已找到但依赖缺失，是分析能否继续的实际障碍。skillenv 默认在 use_skill 时探测依赖并给出缺包说明；只有部署启用安装且用户批准，才创建叠加环境并返回明确解释器路径。依赖来自技能声明的白名单，框架通过 AST 读取注册表字面量，不导入科学模块。安装固定的 wheel，并检查配置和新增依赖冲突，异常时回滚叠加环境。基础环境保持不变，同一分析模块应保持解释器一致。

---

# 18_extensions

扩展能力有两种不同需求。MCP 把外部服务转换成普通工具，通过配置接入 stdio 或 Streamable HTTP，继续走统一工具定义和权限接口。subagent 则接收一个有范围的子任务，使用角色提示、缩小的工具集和独立上下文，复用同一 engine，再把结果返回主任务。用户请求的模块审查可以使用审查子任务，但它不替用户接受结果。独立上下文能减少干扰，不能自动消除模型共同盲点。

---

# 19_observe

任务变长之后，只看最终回答无法知道耗时和调用发生在哪里。工具先经过权限判断，再进入 hooks 拦截和 JSONL 审计，最后执行。observability 组织 interaction、turn、模型请求和工具的跨度关系，记录模型耗时、输入输出 token、工具次数和耗时以及轮次数。它消费已有事件，OpenTelemetry 是可选集成，默认不采集对话和工具正文。被权限拒绝的调用不会进入内侧 hook，因此审计解释也要考虑这一边界。

---

# 20_eval

观测告诉我们发生了什么，评估还要判断任务是否做对。机制回归通过预设调用控制条件，检查工具选择、参数、审批和文件副作用。真实任务评测则在独立工作区运行用例，记录答案、用量和评分，把服务故障与任务得分分开。项目中 evals 负责机制与行为检查，bench 组织真实任务的批量运行和评分。即使这些检查通过，仍然需要检验生物学结论与统计假设，不能直接把执行成功当成科学正确。

---

# 21_boundary

科学方法不应因为 Agent 框架变化而失去独立使用的能力。omicsclaw 负责模型、权限、会话和运行调度，skills 负责方法函数与脚本，两边不相互导入，通过技能说明、依赖字面量和结果文件契约协作。共享的 SDK 和各领域工具承担公共机械工作，科学依赖按任务加载。同一方法可以由 Agent 调用，也可以由研究者直接使用。代价是跨边界数据必须明确表达，接口变化时需要一起核对文件契约。

---

# 22_api_cli

当每个方法只提供命令行时，多步分析往往反复写文件再读文件。项目把计算部分放进函数库，返回数据对象或 Figure；分析步骤通过 load_skill 组合方法、验证结果并显式保存输出。薄 CLI 保留参数解析、文件读写和报告职责。当前有八十三个函数库，五个技能仍保持 CLI，网络获取与计算分开。XCMS 当前仅支持合成演示，真实原始质谱输入会被拒绝，因此不能把接口覆盖理解为所有真实数据路径都已可用。

---

# 23_modules

方法可复用之后，还需要一个让研究者能独立理解和汇报的分析单元。项目以模块组织阶段，例如质控、聚类或注释。课题策略记录问题、数据与跨模块决策；analysis 下保存模块说明、Python 或 R 步骤、参数依据和验证代码；results 下保存图表、中间文件、日志、报告及回放和审查材料。技能是可复用方法，模块是一次具体分析的交付单元，这使方法选择与课题结果各有位置。

---

# 24_replay

参数或输入变化之后，关键是知道哪些结果已经过期。显式读写记录和哈希把步骤代码、输入与输出联系起来，上游或代码变化会让下游标记为 stale。status 只报告状态，run 用于执行过期步骤，replay 重新执行全部步骤并最后运行 Python 验证。依赖追踪只覆盖显式登记的输入输出，并非任意脚本的全量审计。回放成功说明执行过程可以重现，统计假设和生物学解释仍需另外检查。

---

# 25_review

有了回放和报告，结果可以先交给用户查看，再由用户决定是否请求审查和接受。审查材料与对应的回放和文件哈希绑定，材料改变后旧审查不再适用。请求审查只授权检查和报告发现，不自动授权修复、重跑或接受。用户明确接受后冻结模块，后续修改先进入 revise 并保留 baseline；跳过审查也需要明确授权。这让执行完成、独立审查和用户接受成为能够区分的状态。

---

# 26_case

已有四模块记录把这些组件串起来：质控与过滤、预处理聚类、marker 富集，再用 R 对 B 细胞结果作交叉核对。前三模块使用函数库，第四模块使用 Seurat。历史记录中四模块都已接受并冻结，R 独立运行的 CSV 与原件一致，上游改动也能触发下游过期。审查发现并推动补充 counts 逐元素验证、纠正基因与效应值配对。这是已有案例的证据，本轮未重新运行，完整记录中的偏差和限制仍然保留。

---

# 27_discussion

这些组件分别支撑不同的需求：明确边界使框架组件能够替换，函数库使科学方法可以组合，模块证据使分析交付可以检查。下一步更有价值的工作，是选择一个真实课题，测量重放与审查究竟帮助发现了多少问题。组会可以重点讨论任务完成率、错误发现率和生物学结论的可靠性，并据此决定后续优先改进的部分。
