# 01_cover

今天汇报 OmicsClaw 的当前架构，以及各组件为什么按这样的边界划分。我们沿着一条分析请求往下走：先看框架怎样理解请求和调用工具，再看科学方法怎样组合为分析模块，最后看回放、审查与用户验收怎样留下可核对的证据。

本次读取的本地代码快照是 43e9c034，技能加载器识别出八十八个技能，覆盖七个领域；快照中已有二十八个函数库，其中二十七个属于单细胞，一个属于空间组学。这些数字说明接口覆盖范围，不代表所有可选后端都已经经过真实数据验证。正文三十二页，后面四页提供组件目录、方法范围、命令和来源，供讨论时查阅。

# 02_problem

多组学分析的复杂性有两个来源。第一类来自方法与环境：同一个问题可能对应多种算法，而这些算法分别依赖 Python、R、外部命令、数据库和不同输入格式。只让模型记住工具名字，并不能保证方法选得对、环境也能运行。

第二类来自过程与证据。参数或上游数据变了，哪些结果需要重做？离开原来的聊天会话，代码还能不能运行？报告中的结论对应哪一次输出？这些问题需要显式步骤、依赖记录、回放和审查。本页归纳的设计目标，是把可执行的方法接到可检查的分析过程上。后面的组件边界都可以回到这两个问题来理解，而不是单纯追求组件数量。

这个归纳来自 OMICSCLAW.md、docs/FRAMEWORK-REBUILD.md，以及 skills/_sdk/notebook/ 的执行契约。

# 04_map

这张图按照运行职责组织组件。最上方是 CLI、Desktop 和 Channel 三个入口；它们把请求交给 entry，由 entry 组装应用并管理会话。中间的 engine 决定下一步，provider 负责与模型通信，schema 提供双方共同使用的消息和工具调用类型。

这是一张功能关系图，不是逐条 Python 导入图。实际导入边界由源码和边界测试约束；理解职责与核对导入方向，应当分开进行。

# 05_request

以“分析这份单细胞数据”为例，入口首先接入会话、规范输入并排队。随后上下文组件把运行契约、历史、计划和技能目录放入预算允许的窗口。模型根据技能描述选择 use_skill，读取完整说明后再决定具体工具和参数。

工具执行前会经过权限判断，需要时等待审批；bash 可以调用科学脚本或步骤执行器，输出作为观察结果回到模型。模型可能继续调用工具，也可能给出回答。因此，这条路径本质上是多次决策与观察的循环，而不是把一句请求直接翻译成一条命令。

当任务形成分析模块时，还要经过步骤执行、输出检查、replay、review 和 accept。对话回答结束，并不意味着科学结论已经成立，也不意味着用户已经接受模块。相关入口在 omicsclaw/entry/ 和 skills/_sdk/notebook/。

# 06_schema

schema 首先统一组件之间交换的语言，包括 Message、ToolCall、ToolResult、Usage 和 StreamChunk。provider、engine、tools 都依赖这些类型，而 schema 本身不依赖其他项目层，只需要标准库即可导入。这样底层协议不会因为科学依赖或供应商 SDK 的加载问题而失效。

这个边界减少了循环导入，也把供应商特有字段的解释留在适配层。工具参数保留原始 JSON 文本，避免框架提前解析再序列化时无意改变原始协议证据。消息契约还保留 reasoning_content 和 tool 角色，以支持需要历史推理字段的端点。

这里的设计收益是组件可以围绕稳定契约分别测试和替换；代价是跨层变化必须先说明契约如何变化，不能让某个供应商的临时字段自然扩散到整个系统。源码入口是 omicsclaw/schema/。

---

# 07_provider

provider 把模型端点的差异收在适配器里。engine 面向 LLMProvider，只需要传入消息和工具；普通生成、流式生成和配置变体分别通过 generate、generate_stream 和 bind 表达。当前主要适配 OpenAI-compatible 和 Anthropic Messages 两类协议。

模型名称、温度和输出上限属于 provider 实例。需要变体时通过 bind 处理，engine 不需要知道某个厂商怎样命名这些参数。适配层还负责把流式事件、工具调用和错误转换成框架统一的形式。

统一协议可以降低替换模型的成本，却不能保证不同模型有相同的工具选择能力、推理质量或长上下文表现。因此，接口测试和真实模型评估仍然是两类证据。源码可从 omicsclaw/provider/base.py 和 factory.py 开始阅读。

---

# 08_engine

engine 维护 ReAct 主循环：已有消息交给模型，模型提出 ToolCall，执行后产生 ToolResult，再把观察放回消息历史。只要模型还需要工具，就继续这个循环；模型不再请求工具时返回最终回答。

run 和 run_stream 共用一个内核，前者返回完整结果，后者逐步发出事件。这样终止条件、预算和工具处理不会因为输出方式不同而形成两套实现。错误直接抛出，取消继续向上传播，不把失败包装成一个看起来正常的完成结果。

engine 只负责循环本身。提示如何构造、会话如何保存、具体工具怎样实现，都由外部组件承担。这使核心循环能用脚本化 provider 和替代工具测试，而不必启动完整科学环境。实现集中在 omicsclaw/engine/loop.py。

---

# 09_tools

tools 提供注册、暴露定义和执行三个环节。文件、bash、web 和 MCP 工具都进入同一套 registry，工具定义保持稳定的注册顺序，避免同一组工具在不同请求中无故变化。

并发并不是看到多个调用就全部同时启动。工具先声明执行策略，engine 据此编排：明确可安全并发的读取可以一起运行，独占写入会形成边界，再进入下一批调用；结果仍按原调用顺序回填。未声明并发安全的调用默认独占，减少同批写入相互覆盖的问题。

另一个容易忽略的细节是审批等待暂停工具计时。人在判断是否允许时，工具实际上还没有执行，不能把这段时间混进执行超时。registry 提供策略，engine 管理调度，职责分工见 omicsclaw/tools/registry.py 和 omicsclaw/engine/。

# 10_context

上下文预算不是模型窗口的全部容量。需要先扣除输出预留、工具定义和安全余量，剩下的空间才能用于提示和历史。context 在这个预算内组织运行契约、当前目标、技能说明和对话。

压力增加时，处理从正常保留历史，逐步转向卸载长输出、局部总结和全面总结；最紧急时使用不再调用模型的截断路径。长工具输出可以转为文件引用，较旧对话可以压缩，但工具调用和结果的配对关系必须保留，否则下一轮看到的历史可能失去含义。

这里的取舍是信息完整性与窗口成本。压缩机制可以工作，并不表示阈值已经最优；当前压力阈值沿用工程默认值，还没有按项目的真实流量校准。预算和渐进压缩分别见 omicsclaw/context/budget.py、progressive.py。

# 11_memory_plan

memory 保存已经知道的内容，planning 保存接下来要完成的目标。工作区内的 SQLite 数据库保存会话，长期事实通过 FTS5 检索，MEMORY.md 提供有界摘要。历史压缩前先尝试提取长期事实；摘要通过闭包在后续轮次重新读取，使新写入的信息可以被后续判断使用。

PlanBook 则独立于聊天记录。每次模型调用前重新注入计划，恢复会话时还原任务状态，通过 plan_write 更新进展。这样即使较旧对话被压缩，也不必从摘要中猜测还有哪些任务未完成。

两者分开是因为知识和任务状态的更新方式不同。还需要再区分计划与验收：计划里的“完成”只是执行状态，不证明统计结论成立，更不能代替用户接受分析模块。源码位于 omicsclaw/memory/ 和 omicsclaw/planning/。

# 12_skills

技能加载采用先目录、后正文的方式。系统提示只放每个技能的名称和描述，模型先据此选择，再通过 use_skill 取得完整方法说明和技能目录，从而找到脚本、API 与依赖信息。这减少了把全部方法文档塞进上下文的成本。

SKILL.md 是当前单一事实源。description 需要说明何时加载、何时跳过，因为模型主要靠这一行判断；trigger 和 tags 用于人工搜索，不会自动触发技能。缺少必要字段或名称重复的技能会被跳过，并留下可检查的原因。

use_skill 加载的是说明，真正执行仍由 bash 调用脚本或 step runner。当前没有 oc run 命令，也不能从旧运行器文档推断现在仍会自动生成那些旧回执。加载行为见 omicsclaw/skills/index.py，运行约定见 OMICSCLAW.md。

# 13_boundary

框架与科学代码通过文件契约协作。omicsclaw 负责模型、权限、会话和运行调度，不直接导入 skills 的科学实现；skills 负责算法函数、脚本、SDK 和领域共享代码，也不导入 omicsclaw。两侧通过 SKILL.md、依赖注册的纯字面量和结果文件等契约连接。

这个边界有两个收益。科学依赖可以按任务加载，框架启动不必先安装所有方法；同一个技能也可以离开 Agent，由研究人员直接调用。域内共享代码放在 domain/_lib，跨领域机械辅助放在 skills/_sdk，避免科学域之间随意互相依赖。

代价是跨边界信息必须明确序列化，文档、字段或文件结构变化时要同步核对双方。tests/sdk/test_boundary.py 检查导入边界，结果与依赖契约分别可从 skills/_sdk/result.py 和 deps.py 阅读。

# 14_api_cli

函数库迁移把计算与文件副作用分开。_api.py 接受数据和参数，返回数据对象或 Figure；分析步骤通过 load_skill 组合这些函数，负责自己的验证和显式输出。薄 CLI 则继续处理命令行参数、读取输入、写文件和生成报告，让已有脚本使用方式得以保留。

快照中已经迁移二十七个单细胞函数库和 spatial-preprocess。sc-count、sc-fastq-qc、sc-velocity-prep 仍然保留 CLI，步骤通过 run_cli 调用它们，因为原始数据处理与外部流程不一定适合强行包装成内存函数。

迁移要核对旧新 CLI 与 API 的行为，而不只是检查是否出现了一个 _api.py 文件。parity 可以约束固定输入下的数值和输出，但没有安装的后端仍然不能记作验证通过。详细证据见计划 0074 的交付记录和计划 0075。

# 15_modules

分析模块是可以独立解释和交付的阶段，例如 QC、聚类或注释；技能则是可以跨模块复用的方法单元。两者不能混用，一个模块往往会组合多个技能。

跨模块的问题、数据、计划和决策放在 docs/analysis_strategy/STRATEGY.md。每个 analysis 子目录保存模块 README 与 Python、R 步骤，说明方法、输入、参数选择和验证代码；对应的 results 子目录保存图表、中间文件、日志、报告、notebook、provenance、审查和 baseline。

这样的目录安排让代码和输出有明确归属，也为回放和冻结建立边界。聊天中解释过某个选择，并不等于这个选择已经进入可交付材料；应当把必要的方法说明保留到模块文档里。目录契约和执行器实现见 OMICSCLAW.md 与 skills/_sdk/notebook/。

# 16_replay

status、run 和 replay 回答不同问题。status 只观察：哪些步骤已经过期，为什么过期；run 执行当前过期的步骤，适合日常迭代；replay 则把模块步骤全部重新执行，并把 Python validate 步骤放到最后，用于检查完整链路。

过期判断依赖代码和输入文件的哈希。上游输出发生变化，下游记录的输入哈希不再匹配，就会标记 stale；这些依据保存在 manifest 与运行台账中。显式记录依赖比依靠研究人员记住执行顺序更容易核对。

但追踪范围来自 read_input、write_output 等接口，并不是对任意脚本的全量审计。脚本可以成功回放，统计假设仍然可能错误；因此回放解决执行一致性，不能独自解决科学有效性。实现和约定见 skills/_sdk/notebook/ 与 OMICSCLAW.md。

# 17_review

完整回放之后，执行器生成 review_brief，分析者再写 REPORT，解释方法和结果。审查阶段给出 APPROVE 或 REVISE，最后由人确认是否 accept 并冻结模块。这几个状态分别表达运行、解释、检查和接受，不能彼此替代。

框架保存审查原文和 receipt，把审查绑定到对应 replay、步骤和报告哈希。这样修改了材料之后，就不能继续沿用旧审查当作当前版本的依据。receipt 是校验记录，没有数字签名；它提供一致性检查，不是对能同时改写工作区文件和回执的攻击者的防篡改保证。

接受后的模块需要修改时先 revise，保留已接受的 baseline，再重新执行与验收。冻结机制主要防止执行器无意覆盖已接受结果。相关逻辑见 omicsclaw/entry/review.py 和 skills/_sdk/notebook/。

# 18_python_r

Python 和 R 通过明确的文件接口共享证据。Python 每个步骤使用新 kernel，不能依赖前一步留在内存里的变量；R 步骤在一个 Rscript 进程中按顺序执行各个 cell。跨步骤用 MTX、CSV 等文件传递内容，输入输出及其哈希进入记录。

这个选择牺牲了一部分交互式内存复用便利，换来步骤边界更明确，也更容易从头重放。运行记录包含解释器、R 版本、已加载包版本、文件哈希和日志。混合模块最后仍由 Python validate 步骤核对输出，形成同一条证据链。

拼接后的 notebook 用 Markdown 保留 R 代码，不能把它理解成所有内容都变成了可直接执行的 Python 单元；真正重放仍按原始步骤语言执行。混合语言行为和验证范围记录在计划 0074 的交付文档中。

# 19_permission

permission 根据模式、规则和危险命令模式，对工具调用作出 allow、ask 或 deny 的决定。需要审批时，具体入口负责显示卡片并收回用户选择。把决策与展示拆开，三个入口就可以共享同一套政策，而不用各自实现一套判断。

一次允许、会话允许和记住匹配规则，覆盖的授权范围不同。运行姿态包括 default、read-only 和 auto-approve；只读模式不能允许 task 委派一个可能写文件的子任务，因此会拒绝这类调用。即使启用自动允许，危险命令、明确 ask 规则和保护路径仍可能要求审批。

这里的边界也要讲清楚：命令模式匹配可以拦住已知风险，并不能穷尽 shell 的全部语义或绕过形式。权限策略是运行控制的一层，还需要与工具路径约束和隔离环境配合。源码位于 omicsclaw/permission/。

---

# 20_sandbox

sandbox 主要为 bash 提供 Docker 或 Podman 执行环境。默认配置关闭容器网络，并把框架和技能代码只读挂载；工作区供分析读写，内部状态还有遮蔽和交换路径。文件工具仍在宿主机执行，由 Workspace 限定路径，不能把这描述为所有工具都进入了容器。

local-first 说的是分析处理的位置。如果使用远程 provider，发送给模型的消息和工具结果仍然可能离开本机。因此，数据边界还取决于模型部署方式、工具返回内容、权限与网络配置，不能把这个词扩写成绝对的数据不出机承诺。

另外，取消对话不会撤销已经完成的文件写入或其他工具副作用。隔离、取消与回滚是不同能力，汇报时应分别说明。具体边界可从 omicsclaw/sandbox/、工具实现和 provider 调用路径核对。

# 21_skillenv

skillenv 把探测缺包与安装缺包分开。默认 probe 模式在 use_skill 返回的说明里附加环境检查，让模型知道哪些依赖可导入、哪些缺失。只有部署启用 install，并经过工具审批，才会为请求的包创建 overlay，返回明确的解释器路径。

框架通过 AST 读取依赖注册表的纯字面量，不需要导入科学技能。安装限定在技能 Dependencies 的白名单和实际请求范围内，固定 wheel，检查 pip 配置；如果引入新的 pip check 问题就回滚。基础环境保持原状，便于保留已经工作的科学栈。

这也带来解释器管理要求。同一分析模块应尽量保持解释器一致；确实需要切换时，要记录环境和原因，否则文件能接起来，运行条件却可能已经变化。源码在 omicsclaw/skillenv/，依赖名称映射在 skills/_sdk/deps.py。

# 22_extensions

MCP 和 subagent 扩展的对象不同。MCP 把外部服务工具接入进来：服务由 .mcp.json 声明，通过 stdio 或 Streamable HTTP 连接，然后转换成普通 Tool 注册。engine 因而不必为每类服务增加新的循环分支，权限和工具定义继续走统一接口。

subagent 则把一个有明确范围的任务交给独立上下文。角色提示与缩小后的工具集决定它能做什么，仍然复用相同的 engine；子运行由 entry 构造并接收回复，避免子代理包又长出一套应用组装逻辑。

例如 module-reviewer 可以检查模块材料，但不能代替用户接受模块。独立上下文有助于减少当前会话的干扰，却不会自动消除不同模型或同一模型的共同盲点。相关入口是 omicsclaw/mcp/、subagent/ 和 entry/subagent.py。

# 23_observe

工具执行链中，permission 先决定调用能否发生，hooks 位于其内侧，负责拦截和 JSONL 审计，最后才执行实际工具。因此，被权限拒绝的调用不会进入内侧 hook；审计覆盖范围要按这一顺序理解。

observability 从 interaction、turn 到 llm_request、tool 建立运行跨度，并记录六类度量：模型耗时、输入 token、输出 token、工具次数、工具耗时和轮次数。它消费已有 EngineEvent，OpenTelemetry 是可选输出，避免为了观测而让核心循环承担额外日志职责。

默认不采集对话和工具正文载荷，保留时延与调用结构，同时限制内容采集。需要调试正文时应当明确配置和数据范围，不能把度量已开启理解成全部内容都已保存。实现见 omicsclaw/hooks/ 与 observability/。

# 24_entry

entry 是应用的组合根。build_app 把 provider、registry、prompt、memory、permission、sandbox 和 subagents 接成同一个运行时，因此各入口不需要自行拼装内部组件。

会话调度采用同会话串行、跨会话并发。一个会话里的第二次交换排在第一次之后，避免同时修改同一段历史；不同会话可以并行。每次交换有独立 Task，并立即返回可管理的 handle。队列有容量上限，可以取消等待项；事件缓冲也有界，支持观察与续接。

历史提交与工具副作用仍然分开：成功交换才替换已保存会话历史，失败的部分对话不保存，但已经写出的文件不会自动消失。这个选择保持会话状态清晰，也要求上层诚实报告失败前的动作。相关代码见 omicsclaw/entry/assembly.py 和 session.py。

# 28_reliability

近期可靠性修复集中在两类具体失败边界。第一类是模型请求的总 deadline：它覆盖 SDK 重试、首响应等待和流式读取，预算耗尽后 engine 不再额外重试；流清理另有有界时间额度，避免清理过程无限拖延。

这个机制仍有异步执行的限制：如果同步代码阻塞事件循环，异步 deadline 无法及时打断它。第二类是审查材料绑定：审查前后比较文件哈希，框架原样保存 reviewer 回复，accept 再核对 receipt 与 replay。它能发现材料与旧审查不一致，但 receipt 没有签名，不能抵抗同时改写材料和回执的写入者。

目前也没有实现中断交换的自动恢复，已完成的工具副作用不会回滚。详细修复和验证范围保存在 docs/FRAMEWORK-REBUILD.md 的 runtime reliability follow-up 部分。
