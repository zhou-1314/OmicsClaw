# 01_cover

OmicsClaw 要解决的是从分析请求到可审核结果之间的执行问题。当前项目有八十八个技能，覆盖七个领域，其中八十三个提供函数库接口。今天按一次分析会遇到的问题，解释核心组件为什么需要存在，以及它们如何连接请求、执行和证据。技能数量表示能力目录的覆盖范围，不代表所有后端都已完成真实数据验证。

---

# 02_evolution

先看支撑方式为什么发生变化。较多依靠预设工作流的应用，把任务路径、分支条件和异常处理写在代码里，模型在指定节点完成判断。这种方式适合流程稳定、输入边界清楚的任务。随着工具调用、代码生成和多步推理能力发展，模型可以读取工具结果，再提出下一步动作；对于分析路径事先不完全确定的任务，运行时决策变得更可行。

灵活性也带来了工程要求：动作要经过权限检查，长任务需要管理上下文和状态，失败要反馈给后续判断，过程还要能观察和评估。Harness 指围绕模型行动循环提供这些支撑的运行环境。图中左侧强调预设路径，右侧强调判断、执行与观察的反馈循环，表达的是设计重心的变化；Framework 也可以承载这样的循环，固定工作流仍可作为其中的可靠工具。模型决定下一步的能力增强，并不自动保证整个任务可靠完成。

放到 OmicsClaw，质控结果、缺失依赖或某个方法的失败，都可能改变下一步分析。因此项目采用动态决策循环，同时保留科学方法的明确输入输出和模块回放。接下来从这些具体需求展开组件设计。

---

# 03_problem

上一页说明，模型可以根据工具结果继续决定下一步。放到 OmicsClaw，这意味着一次分析会在检查数据、选择方法、运行分析和核验输出之间反复调整。循环越长，积累的信息越多，需要上下文、记忆和计划保留依据与进度；动作可能失败或越界，需要权限、环境与恢复让执行可控地继续；输出最终要支持科研结论，还需要观测、验证和回放把结果连回过程。这些运行支撑共同构成 OmicsClaw 的 Harness。下一页把它们放回同一张系统地图。

---

# 04_map

先把系统看成一条请求流。CLI、Desktop 和 Channel 接收请求，entry 组装运行实例并管理会话；engine 调用模型，provider 处理模型接口差异，schema 定义共同消息。工具层把决策变成动作，权限与沙箱限定执行。科学技能和共享 SDK 产生分析步骤与结果。上下文、记忆、计划、子任务、环境和观测围绕这条路径提供支持。这里画的是职责关系，具体导入方向由代码边界约束。

---

# 05_engine

分析开始时往往还不知道所有后续步骤，所以需要一个能根据观察继续行动的循环。engine 把当前消息交给模型，模型提出工具调用，工具结果再成为下一轮的输入；不再请求工具时，返回最终回答。完整返回和流式输出共享同一个内核，减少两套行为分叉。循环管理执行预算和终止，但把提示构造、会话保存与具体科学方法交给其他组件。执行失败会抛出，取消也继续向外传播。

---

# 06_schema

如果模型接口、主循环和工具各说各话，每次新增能力都要修改多处转换逻辑。schema 提供共同语言：消息、工具调用、工具结果、用量和流式片段。它只依赖标准库，各层都可以使用它，自己不反向依赖项目的其他层。供应商差异留在适配器中。这样，模型适配、执行和工具可以分别演进，也减少了循环导入的问题。

---

# 07_provider

不同模型服务使用不同的消息和工具调用格式。如果这些差异直接进入 engine，替换模型就会影响分析循环。provider 在共同的 LLMProvider 接口下完成请求和返回结果的转换，engine 继续使用 schema 消息。当前项目接入 OpenAI-compatible 与 Anthropic Messages，两条路径都把结果转换回统一契约。图中的往返关系强调接口适配：模型可以替换，工具、会话和分析步骤仍然复用。模型能力本身的差别仍需要通过任务评测判断。

---

# 08_tools

模型提出一个工具调用之后，ToolRegistry 根据名称找到实现，再返回执行结果。基础文件工具分别负责读取说明和输出、创建分析步骤以及修改代码或参数；bash 负责运行 Python、R 和外部命令。科学方法通过技能文档和实现接入，因此主循环继续使用同一套工具接口。图中展示的是基础工具，项目还按职责提供技能加载、计划、记忆和其他工具；四个基础工具并不等于全部工具。

---

# 09_prompt

模型判断所需的信息来自不同位置：OMICSCLAW.md 和安全规则描述分析契约，工具和技能目录描述当前能做什么，环境和记忆摘要提供当前条件。entry 组织这些 Section，PromptAssembler 把它们渲染成系统消息，再与对话历史和当前请求一起发送。计划指导属于系统信息，当前计划还可以在模型调用前注入。汇聚图强调信息有明确来源，避免把规则散落到每个模型调用中。

---

# 10_skills

把八十八份完整方法说明一直放进提示，会挤占数据和结果的空间。技能加载采用先目录、后正文的方式：系统提示先给名称和描述，模型判断需要哪种方法，再通过 use_skill 读取完整说明与所在目录。SKILL.md 集中维护适用条件、跳过条件、接口与依赖。加载说明之后才通过 bash 运行脚本或分析步骤，再读取实际输出。说明文档负责指导选择，执行仍由工具完成。

---

# 11_context

分析历史会积累规则、目标、早期调用、大段工具输出以及最近的调用结果。图中上排表示处理前的历史，下排表示为下一轮留下空间后的工作上下文。较早的长输出可以卸载为文件引用，较旧历史可以总结；近期调用与结果需要保持配对，才能理解某条结论对应什么动作。实际处理由预算压力驱动，依次使用卸载、局部总结、全面总结和紧急截断，矩形宽度只表示关系，不代表实测 token 数或压缩比例。

---

# 12_memory_plan

对话压缩之后，仍要知道已经确认了什么，以及接下来还有什么没做。memory 保存工作区会话和长期事实，通过 SQLite、检索和 MEMORY.md 摘要向后续判断提供依据；planning 用 PlanBook 保存目标、步骤与状态，通过 plan_write 更新。两个方向共同支撑下一次模型判断，执行中得到的新事实与新进度再通过相应机制回写。图中的回写表示信息路径，并不意味着模型每轮都会自动写入。计划标为完成，也不等于科学验收已经通过。

---

# 13_entry

当分析从终端扩展到桌面和消息平台时，不宜为每个界面维护一套运行逻辑。entry 通过 build_app 统一组装模型、工具、提示、记忆、权限、沙箱和子任务。同一会话内的交换串行，避免历史相互覆盖；不同会话可以并发。每次交换有独立任务和可管理句柄，队列与事件缓冲有界，并支持观察和续接。只有成功的交换替换会话历史，从而把界面交互与运行管理分开。

---

# 14_recovery

可修正的工具错误作为观察返回模型。模型读取错误和实际输出，修正输入、参数或代码，再执行并观察新的结果。这条回路说明，恢复依靠新的判断，而不是重复同一个失败动作。模型服务的暂时故障由有限重试和退避处理；预算耗尽或用户取消时则停止。已经完成的文件操作不会随着取消自动回滚，因此恢复后仍要核对真实文件状态。

---

# 15_permission

模型提出工具调用后，PermissionGate 先综合模式、规则和风险检查，决定允许、询问或拒绝。时序图突出需要询问的路径：暂停调用，由入口向用户发起审批，收到决定后才继续执行或者返回拒绝结果。允许的调用可以直接执行，拒绝的调用不会进入工具实现。不同入口承接交互，但权限策略集中管理。授权有一次、会话和规则等不同范围，不能把一次批准解释成对后续所有动作的批准。

---

# 16_sandbox

权限回答能不能做，沙箱进一步限定命令能接触什么。启用时，Docker 或 Podman 接管 bash，默认没有网络，项目代码只读挂载；分析工作区可读写，内部状态通过遮蔽和交换路径处理。宿主机文件工具另由 Workspace 限定路径。分析在本地运行，不代表所有信息都不出机器，因为 provider 仍可能发送上下文和工具结果给远程模型。执行隔离同样不提供对已完成副作用的自动回滚。

---

# 17_skillenv

方法已找到但依赖缺失，是分析能否继续的实际障碍。skillenv 默认在 use_skill 时探测依赖并给出缺包说明；只有部署启用安装且用户批准，才创建叠加环境并返回明确解释器路径。依赖来自技能声明的白名单，框架通过 AST 读取注册表字面量，不导入科学模块。安装固定的 wheel，并检查配置和新增依赖冲突，异常时回滚叠加环境。基础环境保持不变，同一分析模块应保持解释器一致。

---

# 18_extensions

主 Agent 保持课题目标和总体进度。MCP 将外部服务接成统一工具接口，调用后把结果交回主任务；subagent 则接受范围明确的任务与工具，在独立上下文中执行，最后回传摘要或结果。右侧的往返关系借用了子任务隔离图的思路，展示的是 OmicsClaw 的委派机制。独立上下文减少主任务携带的细节，但不能保证消除模型共同盲点。模块审查仍需用户请求，子任务不替用户接受结果。

---

# 19_observe

原图用树状关系展示一次运行如何拆成轮次，再拆成模型请求与工具调用。示例中两轮分别耗时八秒和七秒，组成十五秒的根节点；第一轮模型五秒、工具三秒，第二轮模型六秒、工具一秒，模型节点还记录输入 token。所有这些数值都只是图示，不是 OmicsClaw 的性能结果。项目使用 interaction、turn、llm_request 和 tool 等跨度，关注耗时、token 与工具调用；hooks 另外记录工具审计。借助父子关系，可以从总耗时继续定位到具体调用，而不是只知道整段对话用了多久。

---

# 20_eval

评估从任务用例出发，在独立工作区运行，再收集工具轨迹、文件结果和用量。evals 检查工具参数、权限和文件变化等机制与行为；bench 组织真实任务运行，记录答案、评分和基础设施故障。图中的分支表示两类证据，不意味着两个模块必须共享同一执行入口。服务故障不能直接当成任务质量得分；工程任务通过之后，科研分析仍要检验统计假设和生物学结论。

---

# 21_boundary

科学方法不应因为 Agent 框架变化而失去独立使用的能力。omicsclaw 负责模型、权限、会话和运行调度，skills 负责方法函数与脚本，两边不相互导入，通过技能说明、依赖字面量和结果文件契约协作。共享的 SDK 和各领域工具承担公共机械工作，科学依赖按任务加载。同一方法可以由 Agent 调用，也可以由研究者直接使用。代价是跨边界数据必须明确表达，接口变化时需要一起核对文件契约。

---

# 22_api_cli

当每个方法只提供命令行时，多步分析往往反复写文件再读文件。项目把计算部分放进函数库，返回数据对象或 Figure；分析步骤通过 load_skill 组合方法、验证结果并显式保存输出。薄 CLI 保留参数解析、文件读写和报告职责。当前有八十三个函数库，五个技能仍保持 CLI，网络获取与计算分开。XCMS 当前仅支持合成演示，真实原始质谱输入会被拒绝，因此不能把接口覆盖理解为所有真实数据路径都已可用。

---

# 23_modules

方法可复用之后，还需要一个让研究者能独立理解和汇报的分析单元。项目以模块组织阶段，例如质控、聚类或注释。课题策略记录问题、数据与跨模块决策；analysis 下保存模块说明、Python 或 R 步骤、参数依据和验证代码；results 下保存图表、中间文件、日志、报告及回放和审查材料。技能是可复用方法，模块是一次具体分析的交付单元，这使方法选择与课题结果各有位置。

---

# 24_replay

参数或输入变化之后，关键是知道哪些结果已经过期。显式读写记录和哈希把步骤代码、输入与输出联系起来，上游或代码变化会让下游标记为 stale。status 只报告状态，run 用于执行过期步骤，replay 重新执行全部步骤并最后运行 Python 验证。依赖追踪只覆盖显式登记的输入输出，并非任意脚本的全量审计。回放成功说明执行过程可以重现，统计假设和生物学解释仍需另外检查。

---

# 25_review

有了回放和报告，结果可以先交给用户查看，再由用户决定是否请求审查和接受。审查材料与对应的回放和文件哈希绑定，材料改变后旧审查不再适用。请求审查只授权检查和报告发现，不自动授权修复、重跑或接受。用户明确接受后冻结模块，后续修改先进入 revise 并保留 baseline；跳过审查也需要明确授权。这让执行完成、独立审查和用户接受成为能够区分的状态。

---

# 26_case

已有四模块记录把这些组件串起来：质控与过滤、预处理聚类、marker 富集，再用 R 对 B 细胞结果作交叉核对。前三模块使用函数库，第四模块使用 Seurat。历史记录中四模块都已接受并冻结，R 独立运行的 CSV 与原件一致，上游改动也能触发下游过期。审查发现并推动补充 counts 逐元素验证、纠正基因与效应值配对。这是已有案例的证据，本轮未重新运行，完整记录中的偏差和限制仍然保留。

# 28_paper_design

GeneBench-Pro 的 129 个任务覆盖 10 个领域、21 个子领域。任务给定背景、数据和目标量，让 Agent 自己组织分析；模拟数据用于控制可判定性。图中分支只是对设计思想的概括，不是某个任务的实际轨迹或成绩。

对后续实验的启发是先校准题目本身：正确方法应通过，合理替代方法不应因偏离预设工具而被罚分，科学上错误的路径应产生可区分结果。我们自建题目也要保留这种检验，不能只写一个参考答案就开始比较系统。

来源：GeneBench-Pro，Benchmark Setup、Table 1、Construction, Validation, and Grading；官方 PDF 第 5–7 页。

# 29_paper_finding

论文对部分模型轨迹的定性分析指出，发现诊断线索与落实到后续方法之间存在缺口。这个观察支持提出机制假设，但不直接证明 OmicsClaw 加入某个组件就能改善结果。

作者也承认模拟任务不能覆盖真实研究的全部复杂性，终点二元评分丢失中间阶段差异。因此，我们的验证拟同时保留科学终点和阶段记录；后续再用真实研究数据检验迁移。不能把这篇论文描述成缺少组学覆盖，也不能把过程评分本身宣称为首次提出。

# 30_project_question

OmicsClaw 适合作为机制实验平台：技能与步骤提供方法执行位置，计划与工具循环提供决策接入位置，回放与审查材料帮助追踪变化。右列都是拟增加的研究机制，并非现有工程组件已经具备科学判断能力。

核心假设是：将统计目标、前提和诊断证据显式记录，并让关键证据触发后续决策检查，在同一模型和预算下可能减少无依据结论。需与原始基线及等预算提示增强基线比较，排除仅因为增加提示长度、运行时间或调用次数带来的收益。这里的科学检查与权限审批职责不同，不能用工具获准执行来替代统计有效性判断。

---

# 31_research_mechanisms

沿着一次分析，候选机制分别作用于三个位置。分析前，EstimandGuard 核对实验单位、混杂、重复和统计目标，判断问题是否可回答。分析中，科学错误恢复检查工具没有报错但推断可能无效的情况，选择修正、请求补充或停止，再验证处理是否有效。形成结论时，稳定性机制在预算内选择统计上合理、目标一致或可比较的分析分支，检查结论是否依赖脆弱的分析选择。这些都是拟研究机制。实验上应分别测试单项收益，再检验组合，避免只看到完整系统提高却不知道原因。

首期重点验证诊断后能否采取正确行动；可回答性检查提供行动前提，结论稳定性放在后续扩展，避免一次改变过多机制。

---

# 32_research_benchmark

要检验这些机制，先用成对任务控制科学条件。保持疾病组与对照组表达差异这一研究问题相同：任务 A 提供足够独立 donor，条件与批次可以分离，预期 Agent 给出效应和不确定性；任务 B 让疾病样本全部来自一个批次、对照全部来自另一个批次，预期 Agent 识别完全混杂，停止该效应的独立推断并说明需要怎样补充设计。这里展示的是任务设计方案，不是已有实验结果。

独立组学 Benchmark 同时记录科学成功率、无依据结论率和错误拒绝率，防止系统只会强行输出结果或一律拒绝。OmicsClaw 应当只是被测系统之一，与通用及领域 Agent 在相同条件下比较，评分也不绑定某一种技能或唯一分析工具。这样才能判断改变实验设计后，Agent 是否相应改变了决策。

另记录诊断是否被发现、后续动作是否正确、动作后的结论是否有效，区分发现失败与行动失败。完全混杂任务只停止不可识别的目标效应推断，仍允许有明确限定的描述性分析；接受“缺少怎样的数据”的具体说明。

# 33_research_pilot

第一期收敛到单细胞和 Bulk RNA-seq，规划二十至三十题 Pilot。先校准正确路径、错误路径和合理替代方法，确认任务可以可靠判分，并确实能区分有效与无效推断。校准通过后冻结评分，按任务家族隔离开发集和隐藏测试集，统一模型、可用工具与运行预算。

然后从原始基线出发，分别加入可回答性检查、科学恢复等机制，再检验组合收益；稳定性机制可以在后续扩展。目标是减少无依据结论，同时保持有效任务的完成能力。只有任务和评分成立，才值得继续扩充规模；页面的题量与步骤属于拟定研究计划，不是已经完成的工作。
