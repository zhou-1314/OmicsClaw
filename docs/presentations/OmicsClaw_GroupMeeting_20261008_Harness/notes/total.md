# 01_cover

今天沿着一条分析请求理解 OmicsClaw：模型怎样获得方法说明、怎样调用工具、怎样从结果继续判断，以及分析步骤怎样留下可回放和审核的证据。讲解顺序参考 Tony Bai 的 Harness 教程，每个组件都追问它解决什么问题、输入输出是什么、为什么这样划分边界。

当前代码快照是 90a3bec3。本次加载得到八十八个技能，覆盖七个领域，其中八十三个有函数库，五个保留命令行接口。这个口径已经与上一版更新，接口存在仍不代表所有真实输入和可选后端都通过验证。正文四十页，后面五页用于定位组件、方法、命令、教程对应和来源。

# 02_problem

假设用户要求分析一份单细胞数据，一次模型回答无法提前知道文件质量、实际依赖、批次结构和分析中途的报错。教程第一讲由这个问题引入运行时：模型负责下一步决策，框架负责把环境观察、工具执行和状态持续接回决策。

在 OmicsClaw 中，复杂性一部分来自方法与环境：Python、R 和命令行混用，数据库和输入契约也不同；另一部分来自过程与证据：参数变动后下游是否过期，离开原会话后能否重跑，报告是否对应当前输出。因此需要同时提供可发现的方法、可运行的环境、显式步骤和验证材料。

后面每层都按照同样的追问展开：缺少它会出什么问题，它接收和改变什么，怎样证明行为符合约定。动态 Agent 决策与科学流程的显式依赖可以并存，不需要把所有固定流程或 DAG 都判断为不合理。

# 04_map

这张图按照运行职责组织组件。最上方是 CLI、Desktop 和 Channel 三个入口；它们把请求交给 entry，由 entry 组装应用并管理会话。中间的 engine 决定下一步，provider 负责与模型通信，schema 提供双方共同使用的消息和工具调用类型。

这是一张功能关系图，不是逐条 Python 导入图。实际导入边界由源码和边界测试约束；理解职责与核对导入方向，应当分开进行。

# 05_request

以分析单细胞数据为例，入口先规范输入、接入会话并排队。上下文组件把运行契约、历史、计划、技能目录和预算组织好，模型据此选择 use_skill，读取方法后决定工具和参数。

工具调用经过权限判断，需要时等待审批，再由 bash 执行脚本或分析步骤。观察结果回到模型，触发后续判断。这个结构让模型可以根据实际 QC 或错误调整行动，而不是一次性猜完全部步骤。

分析交付另外包含输出、replay 和报告。当前规则是验证后先展示结果；独立审查只在用户请求后发生，接受模块也需要明确授权。对话结束、结果验证、独立审查和用户接受是不同状态。执行入口见 omicsclaw/entry/，模块机制见 skills/_sdk/notebook/。

# 06_schema

schema 首先统一组件之间交换的语言，包括 Message、ToolCall、ToolResult、Usage 和 StreamChunk。provider、engine、tools 都依赖这些类型，而 schema 本身不依赖其他项目层，只需要标准库即可导入。这样底层协议不会因为科学依赖或供应商 SDK 的加载问题而失效。

这个边界减少了循环导入，也把供应商特有字段的解释留在适配层。工具参数保留原始 JSON 文本，避免框架提前解析再序列化时无意改变原始协议证据。消息契约还保留 reasoning_content 和 tool 角色，以支持需要历史推理字段的端点。

这里的设计收益是组件可以围绕稳定契约分别测试和替换；代价是跨层变化必须先说明契约如何变化，不能让某个供应商的临时字段自然扩散到整个系统。源码入口是 omicsclaw/schema/。

教程第二讲先定义消息再写循环，在项目中可以用一个判断检验这条边界：换模型供应商时，应主要改变 provider 的编码与解码，而不是让 tools 也开始理解厂商字段。

# 07_provider

provider 把模型端点的差异收在适配器里。engine 面向 LLMProvider，只需要传入消息和工具；普通生成、流式生成和配置变体分别通过 generate、generate_stream 和 bind 表达。当前主要适配 OpenAI-compatible 和 Anthropic Messages 两类协议。

模型名称、温度和输出上限属于 provider 实例。需要变体时通过 bind 处理，engine 不需要知道某个厂商怎样命名这些参数。适配层还负责把流式事件、工具调用和错误转换成框架统一的形式。

统一协议可以降低替换模型的成本，却不能保证不同模型有相同的工具选择能力、推理质量或长上下文表现。因此，接口测试和真实模型评估仍然是两类证据。源码可从 omicsclaw/provider/base.py 和 factory.py 开始阅读。

例如 Anthropic 的 tool_use 和 OpenAI 的 tool_calls 都应转换成框架的 ToolCall，让下一层只处理同一种契约。教程第四讲的“适配”在这里表现为具体数据转换，而不是只给 SDK 换一个名字。

# 08_engine

engine 维护 ReAct 主循环：已有消息交给模型，模型提出 ToolCall，执行后产生 ToolResult，再把观察放回消息历史。只要模型还需要工具，就继续这个循环；模型不再请求工具时返回最终回答。

run 和 run_stream 共用一个内核，前者返回完整结果，后者逐步发出事件。这样终止条件、预算和工具处理不会因为输出方式不同而形成两套实现。错误直接抛出，取消继续向上传播，不把失败包装成一个看起来正常的完成结果。

engine 只负责循环本身。提示如何构造、会话如何保存、具体工具怎样实现，都由外部组件承担。这使核心循环能用脚本化 provider 和替代工具测试，而不必启动完整科学环境。实现集中在 omicsclaw/engine/loop.py。

例如 QC 输出暴露批次问题后，下一轮才能据此选择整合策略。实现还区分 CONVERGED、MAX_TURNS 和 TRUNCATED，达到轮数或输出上限不能被读成正常完成，这比只观察模型最后一句话更明确。

# 09_thinking

教程第三讲用两个模型请求实现强制规划：第一次不提供工具，让模型输出规划文本；再把这段文本保留下来，第二次提供工具，让模型行动。这是一种可以比较的控制策略，同时会增加一次调用的延迟和上下文消耗。

OmicsClaw 当前的 engine/loop.py 没有这个强制双阶段。每个正常 ReAct 轮次调用 provider，原生推理由具体模型能力与适配器处理，工具调用仍进入同一循环；reasoning_content 等字段的保留是协议兼容，不等于框架额外发起一次规划请求。

复杂批次设计可能值得先明确分析计划，但读取一个 QC 表不一定需要第二次模型调用。这两个例子说明策略应按任务评估，不能仅从“多想一次”的名字推断收益。本页没有把教程双阶段写成项目已实现功能，也没有宣称哪种方式已经通过性能对照。

# 10_tools

如果主循环里为每个工具写一个分支，新增方法就会不断修改 engine。教程第五讲用 Registry 解决这个耦合：先 register 挂载工具对象，再通过 available_tools 暴露名称、描述和参数定义，模型返回调用后由 execute 根据名称路由执行，结果统一成为 ToolResult。

OmicsClaw 的工具对象同时提供定义、策略与执行行为，registry 保持定义的注册顺序。模型看到的定义与本机策略分开，风险级别、审批方式和并发声明不需要塞进工具参数 Schema。具体部署负责决定这一轮有哪些工具可见。

registry 通过方法形状满足 engine 的 Protocol，无需反向导入 engine。这样可以用简单替身测试循环，也可以独立替换工具实现。实现见 omicsclaw/tools/registry.py、base.py，以及 engine/executor.py。

# 11_primitives

假设每增加一个组学方法就增加一个模型工具定义，方法库扩大时，每轮要携带的名称、参数和说明也会越来越多。教程第六讲从这个问题讨论少量通用原语，OmicsClaw 的科学方法执行也利用了这种组合方式。

read_file 读取说明与结果，write_file 创建分析步骤，edit_file 修改其中一部分，bash 真正运行步骤。模型先用 use_skill 取得方法说明，再写出 step；step 用 load_skill 调函数库，用 run_cli 调 CLI-only 方法。因此新增方法主要增加文档与科学实现，不必给 engine 增加一个算法分支。

项目并不只有这四个工具，还按职责提供技能、计划、记忆、web 和 MCP 等能力。教程对 YOLO 的讨论也不能解释成本项目默认免审批，通用 bash 的副作用仍由权限和执行环境限制。源码见 tools/builtin/，调用约定见 OMICSCLAW.md。

# 12_edit

只修改 QC 阈值时，重写整个脚本会引入无关改动；局部编辑更合适，但模型提供的原文本可能在换行或缩进上偏离文件。edit_file 接受 path、source_text 和 target_text，依次尝试精确匹配、忽略换行差异、忽略首尾空白、忽略缩进四个层级。

每一级都要求只命中一处。多处命中时必须补充上下文，不能默认选第一处；空锚点和纯空白锚点也被拒绝。匹配后先展示 diff 并请求所需审批，批准后在写锁内重新读取文件，如果审批期间文件已经变化就拒绝写入。这避免用户批准的内容与最后实际修改的内容不一致。

模糊匹配会报告 fuzzy 并要求重新读取，尤其是 Python 的缩进直接影响语义。教程第七讲的容错思路在这里还配合唯一性和并发修改检查，具体实现见 omicsclaw/tools/builtin/edit.py。

# 13_parallel

读取两个独立样本表可以并发，但创建步骤文件与随后运行它存在先后关系。模型把两个调用放在同一个响应里，并不构成独立性证明。教程第八讲用 Fork-Join 演示并行和结果保序，OmicsClaw 在生产 registry 上进一步读取 concurrency_safe 声明。

默认启用的安全屏障把连续安全调用组成一批，非安全调用单独执行，前一批结束后才进入后一批。完成快慢不改变结果回填顺序。engine 支持 max_concurrent_tools 配置，零表示不额外设上限；不能把支持配置写成默认存在一个固定并发数。审批等待另外暂停工具计时。

页面的块宽只是流程示意，没有测量耗时。关闭 serialize_unsafe_tools，或使用不提供并发策略接口的执行器，会改变屏障行为，因此结论针对默认生产组装。源码是 engine/executor.py 的 _concurrency_groups 和 tools/registry.py。

# 14_prompt

如果科学规范、环境信息和技能说明散落在调用模型的代码里，修改一条运行约定很难知道影响哪些请求。教程第十讲把 Prompt 当作可组装材料，OmicsClaw 由 entry 决定 Section 顺序，PromptAssembler 读取内容、跳过空段落、统计各段 token，再拼成一个 system 消息。

这些段落包括 OMICSCLAW.md 运行契约、安全与工具指导、计划、沙箱说明、技能目录、环境和长期记忆。教程用 AGENTS.md 演示工作区规则；本项目分析 Agent 的主要运行契约是 OMICSCLAW.md，不能把代码维护说明与分析运行契约混为一谈。

这种分解让输入可检查、可重新组织，但动态段落进入 system prompt 后，变化仍会影响前缀缓存。工具定义顺序稳定并不等于整段提示始终命中缓存。源码见 context/prompt.py、sections.py，以及 entry/assembly.py 的 default_sections。

# 15_skills

技能加载采用先目录、后正文的方式。系统提示只放每个技能的名称和描述，模型先据此选择，再通过 use_skill 取得完整方法说明和技能目录，从而找到脚本、API 与依赖信息。这减少了把全部方法文档塞进上下文的成本。

SKILL.md 是当前单一事实源。description 需要说明何时加载、何时跳过，因为模型主要靠这一行判断；trigger 和 tags 用于人工搜索，不会自动触发技能。缺少必要字段或名称重复的技能会被跳过，并留下可检查的原因。

use_skill 加载的是说明，真正执行仍由 bash 调用脚本或 step runner。当前没有 oc run 命令，也不能从旧运行器文档推断现在仍会自动生成那些旧回执。加载行为见 omicsclaw/skills/index.py，运行约定见 OMICSCLAW.md。

教程第十讲指出把大量技能正文一次塞入提示会增加载荷。这里的渐进加载让目录负责选择、正文负责执行指导；要增加一种方法，首先检查 description 是否足以让模型正确区分相邻任务。

# 16_context

上下文预算不是模型窗口的全部容量。需要先扣除输出预留、工具定义和安全余量，剩下的空间才能用于提示和历史。context 在这个预算内组织运行契约、当前目标、技能说明和对话。

压力增加时，处理从正常保留历史，逐步转向卸载长输出、局部总结和全面总结；最紧急时使用不再调用模型的截断路径。长工具输出可以转为文件引用，较旧对话可以压缩，但工具调用和结果的配对关系必须保留，否则下一轮看到的历史可能失去含义。

这里的取舍是信息完整性与窗口成本。压缩机制可以工作，并不表示阈值已经最优；当前压力阈值沿用工程默认值，还没有按项目的真实流量校准。预算和渐进压缩分别见 omicsclaw/context/budget.py、progressive.py。

教程第十二讲用远期结果掩码与近期输出截断说明这个问题，项目进一步加入 token 预算、卸载与总结层次。比如一个长 QC 日志可以从正文卸载为引用，但对应的调用和结果关系还应保留。

# 17_memory_plan

memory 保存已经知道的内容，planning 保存接下来要完成的目标。工作区内的 SQLite 数据库保存会话，长期事实通过 FTS5 检索，MEMORY.md 提供有界摘要。历史压缩前先尝试提取长期事实；摘要通过闭包在后续轮次重新读取，使新写入的信息可以被后续判断使用。

PlanBook 则独立于聊天记录。每次模型调用前重新注入计划，恢复会话时还原任务状态，通过 plan_write 更新进展。这样即使较旧对话被压缩，也不必从摘要中猜测还有哪些任务未完成。

两者分开是因为知识和任务状态的更新方式不同。还需要再区分计划与验收：计划里的“完成”只是执行状态，不证明统计结论成立，更不能代替用户接受分析模块。源码位于 omicsclaw/memory/ 和 omicsclaw/planning/。

教程第十三讲用 PLAN.md 和 TODO.md 演示状态外部化。当前项目把会话、长期事实和任务计划分开存储，不能仅用“都有 Markdown 文件”来概括它们；下一页再说明计划如何在模型调用前自动出现。

# 18_reminders

读了很多文件以后，模型可能仍在探索，却没有把目标整理成可执行计划。教程第十五讲把提醒放在下一次决策前，OmicsClaw 的 PlanInjector 通过 TurnAugmentor 接口实现了其中的计划提醒。

关键顺序是先 compactor，再向 sent 这个当次请求副本追加内容。如果先提醒再压缩，提醒可能立即被压掉；如果写回 history，重复注入又会让历史不断膨胀。当前默认连续八个只读轮次且没有计划时，提醒调用 plan_write，一次 exchange 最多触发一次。已有计划时，每次调用重新呈现未完成项，计划工具更新后下一轮可见。

这比仅依赖模型记得去读 TODO 文件更明确，但它不是检测所有重复调用或死循环的通用系统。提示是否改善复杂任务完成率仍需评估。实现见 planning/injector.py 与 engine/loop.py。

# 19_recovery

错误恢复首先要判断谁拥有这个错误。如果编辑锚点不唯一，或分析参数不合法，简单重发同一个调用通常没有意义。工具将 is_error 观察返回给模型，由模型重新读取内容、修正参数，再决定下一步；这类反馈是决策输入。

如果模型请求遇到网络故障、限流或服务端错误，则由 engine/retry.py 按有限预算退避重试。网络和生成错误有不同预算，其他请求类四百状态不盲目重复。总 deadline 已耗尽时不再叠加重试，用户取消也继续传播。

教程第十四讲演示了统一恢复提示模板仓库；当前项目没有同款组件，而是采用工具反馈、provider 错误分类和分层重试。恢复也不等于回滚：已完成的文件副作用仍在，自动续跑中断交换也不能据此宣称已经实现。

# 20_entry

entry 是应用的组合根。build_app 把 provider、registry、prompt、memory、permission、sandbox 和 subagents 接成同一个运行时，因此各入口不需要自行拼装内部组件。

会话调度采用同会话串行、跨会话并发。一个会话里的第二次交换排在第一次之后，避免同时修改同一段历史；不同会话可以并行。每次交换有独立 Task，并立即返回可管理的 handle。队列有容量上限，可以取消等待项；事件缓冲也有界，支持观察与续接。

历史提交与工具副作用仍然分开：成功交换才替换已保存会话历史，失败的部分对话不保存，但已经写出的文件不会自动消失。这个选择保持会话状态清晰，也要求上层诚实报告失败前的动作。相关代码见 omicsclaw/entry/assembly.py 和 session.py。

这也承接教程第九和十一讲：输出从循环中解耦，入口适配事件；同会话的第二条指令先排队，避免两次交换同时覆盖历史。工作区会话隔离不等于两个会话绝不会访问同一个分析文件，文件副作用仍由执行边界管理。

# 21_surfaces

教程第九讲用 Reporter 把终端输出与飞书发送解耦。在 OmicsClaw 中，对应的是 engine 发出事件，由 entry 下不同入口适配；CLI、Desktop 和 Channel 都共用 AgentApp，避免每个入口复制一套执行循环。

CLI 提供 REPL、审批和会话恢复；Desktop 提供 HTTP、SSE、审批与文件服务；Channel 支持七种平台，并要求 owner allowlist。当前后端具备审批和中止端点，独立模块审查由当前请求显式开启，不能因为前一轮批准过审查就长期保持开启。

本仓库负责后端政策、执行、持久化和 HTTP 契约，单独的 OmicsClaw-App 仓库负责 Electron、Next.js 和 SSH 隧道。本次没有重新检查 App 源码或运行端到端客户端，因此后端接口核对不等于本次客户端体验验收。

# 22_permission

permission 根据模式、规则和危险命令模式，对工具调用作出 allow、ask 或 deny 的决定。需要审批时，具体入口负责显示卡片并收回用户选择。把决策与展示拆开，三个入口就可以共享同一套政策，而不用各自实现一套判断。

一次允许、会话允许和记住匹配规则，覆盖的授权范围不同。运行姿态包括 default、read-only 和 auto-approve；只读模式不能允许 task 委派一个可能写文件的子任务，因此会拒绝这类调用。即使启用自动允许，危险命令、明确 ask 规则和保护路径仍可能要求审批。

这里的边界也要讲清楚：命令模式匹配可以拦住已知风险，并不能穷尽 shell 的全部语义或绕过形式。权限策略是运行控制的一层，还需要与工具路径约束和隔离环境配合。源码位于 omicsclaw/permission/。

教程第十六讲用飞书消息解除阻塞来解释审批。项目把它推广成入口提供的审批通道，执行器等待决定；这段人类等待不计入工具自己的执行时间，审批本身仍有独立的生命周期与超时。

# 23_sandbox

sandbox 主要为 bash 提供 Docker 或 Podman 执行环境。默认配置关闭容器网络，并把框架和技能代码只读挂载；工作区供分析读写，内部状态还有遮蔽和交换路径。文件工具仍在宿主机执行，由 Workspace 限定路径，不能把这描述为所有工具都进入了容器。

local-first 说的是分析处理的位置。如果使用远程 provider，发送给模型的消息和工具结果仍然可能离开本机。因此，数据边界还取决于模型部署方式、工具返回内容、权限与网络配置，不能把这个词扩写成绝对的数据不出机承诺。

另外，取消对话不会撤销已经完成的文件写入或其他工具副作用。隔离、取消与回滚是不同能力，汇报时应分别说明。具体边界可从 omicsclaw/sandbox/、工具实现和 provider 调用路径核对。

# 24_skillenv

skillenv 把探测缺包与安装缺包分开。默认 probe 模式在 use_skill 返回的说明里附加环境检查，让模型知道哪些依赖可导入、哪些缺失。只有部署启用 install，并经过工具审批，才会为请求的包创建 overlay，返回明确的解释器路径。

框架通过 AST 读取依赖注册表的纯字面量，不需要导入科学技能。安装限定在技能 Dependencies 的白名单和实际请求范围内，固定 wheel，检查 pip 配置；如果引入新的 pip check 问题就回滚。基础环境保持原状，便于保留已经工作的科学栈。

这也带来解释器管理要求。同一分析模块应尽量保持解释器一致；确实需要切换时，要记录环境和原因，否则文件能接起来，运行条件却可能已经变化。源码在 omicsclaw/skillenv/，依赖名称映射在 skills/_sdk/deps.py。

# 25_extensions

MCP 和 subagent 扩展的对象不同。MCP 把外部服务工具接入进来：服务由 .mcp.json 声明，通过 stdio 或 Streamable HTTP 连接，然后转换成普通 Tool 注册。engine 因而不必为每类服务增加新的循环分支，权限和工具定义继续走统一接口。

subagent 则把一个有明确范围的任务交给独立上下文。角色提示与缩小后的工具集决定它能做什么，仍然复用相同的 engine；子运行由 entry 构造并接收回复，避免子代理包又长出一套应用组装逻辑。

例如 module-reviewer 可以检查模块材料，但不能代替用户接受模块。独立上下文有助于减少当前会话的干扰，却不会自动消除不同模型或同一模型的共同盲点。相关入口是 omicsclaw/mcp/、subagent/ 和 entry/subagent.py。

教程第十七讲强调把大量探索留在子上下文，只把结果返回主任务。这里的取舍是主上下文更短，但总结可能遗漏信息，所以审查需要绑定具体材料；当前 module-reviewer 也只在用户明确请求时运行。

# 26_observe

工具执行链中，permission 先决定调用能否发生，hooks 位于其内侧，负责拦截和 JSONL 审计，最后才执行实际工具。因此，被权限拒绝的调用不会进入内侧 hook；审计覆盖范围要按这一顺序理解。

observability 从 interaction、turn 到 llm_request、tool 建立运行跨度，并记录六类度量：模型耗时、输入 token、输出 token、工具次数、工具耗时和轮次数。它消费已有 EngineEvent，OpenTelemetry 是可选输出，避免为了观测而让核心循环承担额外日志职责。

默认不采集对话和工具正文载荷，保留时延与调用结构，同时限制内容采集。需要调试正文时应当明确配置和数据范围，不能把度量已开启理解成全部内容都已保存。实现见 omicsclaw/hooks/ 与 observability/。

教程第十八讲问一次任务用了多少资源，第十九讲继续问耗时发生在哪里。跨度关系让同一轮的模型等待和多个工具运行可以分别定位。token 是计量数据，换算货币还需要具体模型价格，当前页面没有假设固定单价。

ScriptedProvider 预设模型会发出的调用和回复，用来稳定复现机制问题。例如 ToolCalled、ToolArgs 检查动作与参数，NoWriteOutside 检查越界副作用，审批和调用次数也有对应检查。这些能发现组装路径没有接通的问题，却不能证明真实模型一定会选择正确技能。

# 28_boundary

# 30_modules

分析模块是可以独立解释和交付的阶段，例如 QC、聚类或注释；技能则是可以跨模块复用的方法单元。两者不能混用，一个模块往往会组合多个技能。

# 31_replay

status、run 和 replay 回答不同问题。status 只观察：哪些步骤已经过期，为什么过期；run 执行当前过期的步骤，适合日常迭代；replay 则把模块步骤全部重新执行，并把 Python validate 步骤放到最后，用于检查完整链路。

过期判断依赖代码和输入文件的哈希。上游输出发生变化，下游记录的输入哈希不再匹配，就会标记 stale；这些依据保存在 manifest 与运行台账中。显式记录依赖比依靠研究人员记住执行顺序更容易核对。

但追踪范围来自 read_input、write_output 等接口，并不是对任意脚本的全量审计。脚本可以成功回放，统计假设仍然可能错误；因此回放解决执行一致性，不能独自解决科学有效性。实现和约定见 skills/_sdk/notebook/ 与 OMICSCLAW.md。

# 32_review

当前交互把验证结果、独立审查和接受分开。分析完成 replay 并写出 REPORT 后，应立即展示结果；独立审查默认关闭。Desktop 的 Independent review 按钮开启一个新回合，只为这一回合授权审查，后续普通回合恢复关闭。CLI 和 Channel 也只在当前用户明确请求时审查。

用户请求审查后，reviewer 检查对应模块材料，报告 findings。框架保存原始回复与 receipt，绑定 replay 和文件哈希；材料变化后不能沿用旧审查。这个请求不授权自动修改问题、重跑分析或接受模块。receipt 只是校验记录，没有数字签名。

accept 必须由用户明确决定。默认不审查不等于已经批准；用户若明确接受且明确跳过审查，才使用 --skip-review，图中虚线表达这条路径。修改已接受模块先 revise，保留 baseline。依据是当前 OMICSCLAW.md 与 entry/review.py。

# 33_python_r

Python 和 R 通过明确的文件接口共享证据。Python 每个步骤使用新 kernel，不能依赖前一步留在内存里的变量；R 步骤在一个 Rscript 进程中按顺序执行各个 cell。跨步骤用 MTX、CSV 等文件传递内容，输入输出及其哈希进入记录。

这个选择牺牲了一部分交互式内存复用便利，换来步骤边界更明确，也更容易从头重放。运行记录包含解释器、R 版本、已加载包版本、文件哈希和日志。混合模块最后仍由 Python validate 步骤核对输出，形成同一条证据链。

拼接后的 notebook 用 Markdown 保留 R 代码，不能把它理解成所有内容都变成了可直接执行的 Python 单元；真正重放仍按原始步骤语言执行。混合语言行为和验证范围记录在计划 0074 的交付文档中。

# 36_reliability

近期可靠性修复集中在两类具体失败边界。第一类是模型请求的总 deadline：它覆盖 SDK 重试、首响应等待和流式读取，预算耗尽后 engine 不再额外重试；流清理另有有界时间额度，避免清理过程无限拖延。

这个机制仍有异步执行的限制：如果同步代码阻塞事件循环，异步 deadline 无法及时打断它。第二类是审查材料绑定：审查前后比较文件哈希，框架原样保存 reviewer 回复，accept 再核对 receipt 与 replay。它能发现材料与旧审查不一致，但 receipt 没有签名，不能抵抗同时改写材料和回执的写入者。

目前也没有实现中断交换的自动恢复，已完成的工具副作用不会回滚。详细修复和验证范围保存在 docs/FRAMEWORK-REBUILD.md 的 runtime reliability follow-up 部分。

# 40_discussion

接下来最值得回答的，不只是还能增加多少工具，而是这些设计在真实科研任务中带来了什么可测量的收益。可以选择一个空间组学课题，事先约定数据、目标、方法和评估指标，再比较不同执行与审查方式下的重现率、错误发现情况和时间成本。

讨论可以围绕空间数据优先级、真实后端覆盖，以及如何同时评价可重现性与统计有效性展开。后面的备份页提供组件目录、七领域任务范围、实际命令和证据出处，方便针对具体问题进一步核对。

# 41_components

这页按职责提供代码定位。决策与执行包括 schema、provider、engine、tools、permission 和 sandbox；知识与任务状态包括 context、skills 加载器、memory 和 planning；组装与扩展包括 entry、launch、MCP、subagent、hooks、observability 和 evals。

科学方法侧，skillenv 负责依赖探测与 overlay，skills/_sdk 提供机械辅助和步骤执行器，domain/_lib 放域内共享实现，_api.py 暴露可组合的方法函数。evals 则让框架行为测试和真实模型评估有独立位置，避免与科学算法测试混成一个数字。

还需要留意历史文档：common、attachments 仍在当前快照中，而 remote、routing、surfaces、ensemble、runtime 已不在当前代码树。不要根据旧目录说明去使用已删除入口。本页依据实际目录枚举和 sources/repository_snapshot.json。

# 42_domains

七领域目录说明可以选择哪些任务，同时要区分计算入口与上游处理。单细胞三十个技能覆盖 QC、双细胞、聚类、marker、注释、整合、轨迹、velocity、扰动与 ATAC；空间十七个涉及预处理、分区、空间统计、注释、解卷积、配准、通信与轨迹。

bulk RNA-seq 十四个包含差异、富集、共表达、去卷积与生存分析；基因组十个包含 QC、比对结果和变异结果解析、CNV 与组装统计。这里特别说“结果”，因为当前若干函数处理的是已有文件，不能冒称执行了 FASTQ 到变异检测的全部上游流程。

蛋白组八个涉及 DIA/DDA 结果、PTM、网络和生物标志物；代谢组八个涉及表格处理、标准化、注释和通路，XCMS 的真实原始质谱限制另见进展页。文献技能处理 PDF、DOI、PubMed、GEO 与数据线索，网络获取明确分离。

# 43_commands

模块命令由 skills/_sdk/notebook/run.py 提供。new qc 创建模块与策略模板，run 执行过期步骤，status 显示状态和原因，replay 完整重跑并把 validate 放在最后。accept 配合当前 review 文件，在用户明确同意后接受并冻结模块。

独立审查默认关闭，不能因此自动认为结果已获批准。用户明确接受且明确要求跳过审查时，才使用 --skip-review 并保存用户的理由。已接受模块要修改，应先 revise 并保留 baseline。

执行器在前台运行，以取得完整输出与失败信息；从实际分析工作区调用时，用完整的仓库执行器路径或已配置入口。oc 仍是 cli、desktop、channel 的入口选择器，当前没有 oc run。命令和授权边界以 OMICSCLAW.md 及执行器帮助为准。

# 44_mapping

教程前五讲建立架构、消息与循环、Thinking、Provider 和 Registry，对应本报告的核心执行层。六到十讲讨论基础原语、编辑容错、并发、飞书输出和提示组装，对应物理交互与运行规范。十一到十五讲讨论会话、压缩、记忆计划、恢复与提醒，对应状态和上下文管理。十六到二十讲再用审批、子任务、成本、追踪和 benchmark 约束与度量执行。

这些是讲解关系，不是逐项照搬实现。最需要注意的差别是当前没有强制双阶段 Thinking，默认生产工具调度有安全批次屏障，记忆与计划分别使用 SQLite、摘要和 PlanBook，恢复与提醒也没有被扩写成通用模板仓库或全能死循环检测器。

MCP、skillenv、科学函数库、分析模块和 replay 等内容则按 OmicsClaw 的实际需求补充。逐讲页码、源码和差异保存在 sources/tutorial_alignment.md，原文件路径与哈希见 tutorial_manifest.json，教程作者是 Tony Bai。
